# 全局大盘指标口径说明

> 覆盖 Cockpit 驾驶舱全部页面的指标：运维监控（monitor）、故障排查（fault）、总览（overview）、告警列表。
> 每个指标给出：计算逻辑、涉及 Doris 表、完整 SQL 形态、是否动态配置。
> 本文与代码的对应关系以当前版本为准，代码位置均标注 `文件:行号`（行号随迭代可能漂移，方法名稳定）。

## 1. 数据链路总览

```
Agent / nginx access log
    │  OTLP / SkyWalking / nginx-log
    ▼
ai-apm-ingest（转换器打错误/慢调用标记，按分钟聚合）
    │  OtelConverter / NginxOtlpConverter / SkyWalkingConverter
    ▼
Kafka → DcSpanUtil（指标抽取）
    │  入口 span → metric_service（服务维度 rollup）
    │  http 组件 span → metric_service_http（含 httpCode/url/srcService 维度）
    │  异常入口 span → metric_service_exception
    ▼
Doris（AGGREGATE KEY 表，cnt/error/sumDuration 为 SUM 列）
    ▼
ai-apm-web 查询层
    │  MetricQueryBuilder（SQL 文本）→ MetricQueryService / ApmReadRepository（执行）
    │  CockpitMetricPortalService / CockpitPortalService（看板编排）
    ▼
前端页面（monitor.vue / fault/ / overview.vue）
```

### 关键写入侧定义（理解一切指标的前提）

| 标记 | 定义 | 代码位置 |
|---|---|---|
| `error`（错误） | OTLP：span Status == `STATUS_CODE_ERROR`（不看 HTTP 状态码，4xx 是否算错取决于 agent）；nginx：`status >= 500`（4xx 不算）；SkyWalking：`isError` 原样 | OtelConverter.java:482,520；NginxOtlpConverter.java:148；SkyWalkingConverter.java:82 |
| `slow`（慢调用，500ms 档） | 接入层硬编码：耗时 > 500ms 记 1（`duration > 500_000_000L`） | OtelConverter.java:521；SkyWalkingConverter.java:83 |
| `durationRange`（耗时分桶标签） | 按 `UPPER_MS = {50,100,200,500,1000,3000}` 分桶：`0-50ms / 50-100ms / 100-200ms / 200-500ms / 500-1000ms / 1000-3000ms / 3000ms+`，>3000ms 即 `3000ms+` | DurationRangeUtil.java:5-20 |
| `exception`（异常） | 入口 span（isIn=1）且 `error > 0` 才写 `metric_service_exception` | DcSpanUtil.serviceExceptionMetric:369-375 |
| 入口口径 | `metric_service` 表只由入口 span（isIn=1）写入，"服务入口"语义由此保证 | DcSpanUtil.isServiceEntrySpan:89-100 |

## 2. 运维监控页（monitor.vue）

### 2.1 KPI 卡 —— `POST /cockpit/kpiSummary`

后端：`CockpitMetricPortalController` → `CockpitMetricPortalService.kpiSummary`。
今日/昨日两个窗口并行计算；**sum 语义走单次直接聚合（directTotal），avg 语义走分桶序列再聚合**。
`metric` 到表的解析：`MetricIdentifierParser.parse`（`service.error` → 表 `metric_service`、列 `error`）。

#### ① 请求量（`service.cnt`，sum）

- 计算逻辑：窗口内入口请求数求和。sum 语义走 `directTotal`，1 次查询。
- 表：`metric_service`
- SQL（`MetricQueryBuilder.metricFieldTotalSql`）：

```sql
SELECT SUM(`cnt`) AS metric_total, COUNT(*) AS matched_rows
FROM {db}.`metric_service`
WHERE `ts` >= {from_ms} AND `ts` < {to_ms}
  AND {metric_time 分区裁剪}
  [AND `service` IN ('筛选服务', ...)]
```

- 动态配置：无（跟随页面时间窗与服务筛选）。

#### ② 异常数（`service.exception.cnt`，sum）

- 计算逻辑：窗口内入口异常次数求和。**与耗时无关**（见 1 关键写入侧定义）。
- 表：`metric_service_exception`
- SQL：同 ①，表换为 `metric_service_exception`、列 `cnt`。
- 动态配置：无。

#### ③ 错误率（`service.error`，avg，slaMode=false）

- 计算逻辑：**各时间桶 `SUM(error)` 的平均值**（avg 语义，非占比）。下钻时用 `countMetric=service.cnt` 的序列按桶乘出错误次数。
- 表：`metric_service`
- SQL（`metricFieldSeriesSql`，走 metricChart 分组/全局路径）：

```sql
SELECT CAST(FLOOR(`ts` / 1000 / {bucket_sec}) * {bucket_sec} AS BIGINT) AS epoch_sec,
       SUM(`error`) AS metric_value
FROM {db}.`metric_service`
WHERE `ts` >= {from_ms} AND `ts` < {to_ms}
  AND {分区裁剪}
  [AND `service` IN (...)]
GROUP BY epoch_sec
ORDER BY epoch_sec ASC
```

- 动态配置：无。

#### ④ 可用性 SLA（`service.error`，avg，slaMode=true）

- 计算逻辑：`SLA = 100 − 错误率`（前端 `monitor.vue loadKpis` 对 slaMode 项取反）。
- 表 / SQL：同 ③。
- 动态配置：无。

#### ⑤ 慢调用（`service.http.cnt` + `durationRange='3000ms+'` 过滤，sum）

- 计算逻辑：窗口内落在 `durationRange='3000ms+'` 桶的请求数（即**单次请求耗时 >3s** 的请求数，`SUM(cnt)`）。
  不用 `slow` 列的原因：其阈值写死 500ms 不可配，且 `slowCnt/verySlowCnt` 列从未写入（恒 0）。
- 表：`metric_service_http`
- SQL：同 ①，表换为 `metric_service_http`，并追加（长连接排除见 §5）：

```sql
SELECT SUM(`cnt`) AS metric_total, COUNT(*) AS matched_rows
FROM {db}.`metric_service_http`
WHERE `ts` >= {from_ms} AND `ts` < {to_ms}
  AND {分区裁剪}
  AND `durationRange` = '3000ms+'          -- 慢调用口径
  [AND `service` IN (...)]
  [AND `service` NOT IN ('长连接服务', ...)] -- 长连接排除
```

- 动态配置：
  - 口径（3000ms+）硬编码在前端 `monitor.vue` 的 `SLOW_FILTERS` 常量，改阈值只动这一处；
  - 长连接服务列表（`longConnServices`）动态可配，见 §5。

### 2.2 核心趋势 / 趋势分组卡 —— `POST /cockpit/metricTrends`

- 计算逻辑：与 KPI 同源指标的分桶序列；无服务筛选时全局单序列（1 次查询），有服务筛选时按 service 分组（1+N 次查询）后跨服务合并。昨日曲线 = 等长前一日窗口。
- 表：`metric_service` / `metric_service_exception`（随指标）。
- SQL：同 2.1-③。
- 动态配置：无。

### 2.3 服务排行 —— `POST /cockpit/serviceRanking`

- 计算逻辑：按服务分组聚合单指标取 Top N。
  - `includeSeries=false` 且 `aggs=sum`（排行/慢调用值查询）：**1 次查询**直接取分组总量（`metricTopGroupTotals`）；
  - `includeSeries=true`（下钻需要序列）：单次 `GROUP BY service, epoch_sec` 查询后 Java 拆分补零（`metricGroupBucketSeries`）。
- 表：随指标（`metric_service` / `metric_service_http`）。
- SQL：
  - 总量模式（`metricTopGroupsSql`，LIMIT 实际钳位 50）：

    ```sql
    SELECT `service` AS group_value, SUM(`cnt`) AS metric_total
    FROM {db}.`metric_service`
    WHERE `ts` >= ... AND `ts` < ...
      AND {分区裁剪} AND `service` IS NOT NULL AND `service` != ''
      [AND 标签过滤（含长连接 NOT IN）]
    GROUP BY `service`
    ORDER BY metric_total DESC
    LIMIT 50
    ```

  - 序列模式（`metricGroupBucketSeriesSql`）：

    ```sql
    SELECT `service` AS group_value,
           CAST(FLOOR(`ts` / 1000 / {bucket_sec}) * {bucket_sec} AS BIGINT) AS epoch_sec,
           SUM(`cnt`) AS metric_value
    FROM {db}.`metric_service_http`
    WHERE ... AND `durationRange` = '3000ms+'
      AND `service` NOT IN ('长连接服务', ...)
    GROUP BY group_value, epoch_sec
    ORDER BY epoch_sec ASC
    ```

- 动态配置：长连接服务排除（见 §5）。

### 2.4 接口排行 / 接口趋势下钻 —— `POST /cockpit/serviceEndpoints`

- 计算逻辑：单服务按 `resource`（接口）分组 Top N，今日/昨日各一次分组查询。
- 表：`metric_service_http`（resource/url 维度在此表）。
- SQL：同 2.3-序列模式，分组列换 `resource`（无数据回退 `url`），并追加 `AND service = '{当前服务}'`。
- 动态配置：长连接排除（慢调用口径时）。
- 已知优化点：该路径仍为 1+N（逐分组时序查询），可复用 `metricGroupBucketSeries` 收敛为 1 次，未实施。

## 3. 故障排查页（fault/）

### 3.1 服务健康红绿灯 —— `POST /cockpit/trafficLight`

后端：`CockpitPortalService.servicesHealth`。

- 计算逻辑：取全量服务集（`basicServices`，先按 `longConnServices` 剔除长连接服务），按分钟桶逐桶输出每个服务的 value 与红绿灯颜色：
  - `orderBy=alarm`：value = 该服务当分钟在告警存储（AlarmStore）中的**活动告警数**（`buildAlarmCountsByBucket`，告警活动区间 [triggeredAt, resolvedAt) 与分钟桶重叠计数）；
  - `orderBy=exception`：value = 该服务当分钟 `SUM(error)`（`exceptionCountsForMinute`，数据来自 trafficLightSql）；
  - 颜色：`valueColor(value)`——`value >= redThreshold → red`，`>= yellowThreshold → yellow`，否则 green；
  - 每桶按 value 降序截断 `showServiceNumber`（默认 10）。
- 表：`metric_service`（trafficLightSql）+ 内存告警存储。
- SQL（`MetricQueryBuilder.trafficLightSql`）：

```sql
SELECT FROM_UNIXTIME(FLOOR(`ts` / 60000) * 60) AS ts,
       `service`,
       SUM(`error`) AS error_cnt,
       SUM(`cnt`) AS total_cnt
FROM {db}.`metric_service`
WHERE `ts` >= ... AND `ts` < ... AND {分区裁剪}
GROUP BY ts, `service`
ORDER BY ts ASC
```

  返回后按 `longConnServices` 剔除（`TrafficLightService.trafficLight` 出口过滤）。
- 动态配置：`alarmRed`(2) / `alarmYellow`(1) / `exceptionRed`(10) / `exceptionYellow`(2) / `showServiceNumber`(10) —— 动态可配。

### 3.2 服务告警趋势 —— `POST /cockpit/countServiceAlarms`

- 计算逻辑：按 interval 分桶，逐桶计数：
  - `orderBy=alarm`：该桶内**活动告警数**（AlarmStore 重叠计数，同 3.1）；
  - `orderBy=exception`：该桶内 `SUM(error)` 求和（trafficLightSql）；
  - 每桶附红绿灯颜色（`valueColor`，阈值同上）。
- 表：内存 + `metric_service`。
- 动态配置：`alarmRed/alarmYellow/exceptionRed/exceptionYellow`。

### 3.3 红黄出现次数 —— `POST /cockpit/countServiceAlarmsTotal`

- 计算逻辑：展示窗口（默认 5 分钟，`DISPLAY_WINDOW_MS`，可用 `windowEnd` 平移）内 `servicesHealth` 的 `serviceOrders` 中 `trafficLight ∈ {yellow, red}` 的出现次数，分 alarm / exception 两个视角返回。
- 动态配置：同 3.1。

## 4. 总览页（overview.vue）

### 4.1 服务实体卡 —— `POST /cockpit/workbench/getEntityDataCount`

后端：`CockpitPortalService.entityData`，两路并发。

#### ① 服务总数（total）

- 计算逻辑：窗口内去重服务数（COUNT(DISTINCT)，**不含长连接排除**——总数语义是"有多少服务实体"）。
- 表：`metric_service`
- SQL（`countDistinctServicesSql`）：

```sql
SELECT COUNT(DISTINCT `service`) AS total_cnt
FROM {db}.`metric_service`
WHERE `ts` >= ... AND `ts` < ... AND {分区裁剪}
  AND `service` IS NOT NULL AND `service` != ''
```

#### ② 异常服务趋势（errCnt + healthRangeScoreList）

- 计算逻辑：按分钟桶统计**不健康服务数**。不健康 = 非 green（`trafficLightColor` 规则下推 SQL）：
  `total_cnt < minRequestCount`（灰，低流量也算）OR `total_cnt <= 0` OR `error_cnt/total_cnt > errorRateThreshold/2`（黄/红）。
  **已按 `longConnServices` 排除**（SQL `AND service NOT IN (...)`）。
  前端取最后一个桶作为 `errCnt`，全量桶作为趋势。
- 表：`metric_service`
- SQL（`unhealthyServiceTrendSql`）：

```sql
SELECT ts_millis, COUNT(*) AS unhealthy_count
FROM (
    SELECT FLOOR(`ts` / 60000) * 60000 AS ts_millis,
           `service`,
           SUM(`error`) AS error_cnt,
           SUM(`cnt`) AS total_cnt
    FROM {db}.`metric_service`
    WHERE `ts` >= ... AND `ts` < ... AND {分区裁剪}
    GROUP BY ts_millis, `service`
) t
WHERE (`total_cnt` < {minRequestCount}
   OR `total_cnt` <= 0
   OR `error_cnt` * 1.0 / NULLIF(`total_cnt`, 0) > {errorRateThreshold} / 2)
   AND `service` NOT IN ('长连接服务', ...)
GROUP BY ts_millis
ORDER BY ts_millis ASC
```

- 动态配置：`errorRateThreshold`(0.05) / `minRequestCount`(10) / `longConnServices` —— 动态可配（§5）。

### 4.2 告警等级统计 —— `POST /cockpit/workbench/getAlarmCount`

- 计算逻辑：遍历**内存告警存储**（`AlarmStore.listRecent`），按 `triggeredAt` 落在窗口内过滤，按级别分桶：`portalAlarmLevel`——`critical/error → 3（严重 matter）`，`其余 → 2（一般 minor）`，`noData` 桶当前恒为 0（映射函数不会返回 <2）。**不查 Doris**。
- 数据源：`AlarmStore`（内存 LinkedHashMap，可选持久化到 `config_event`）。
- 动态配置：无（级别由规则评估结果决定）。

### 4.3 最新告警列表 —— `POST /alarm/list`（AlarmApi.getAlarmListNew）

- 计算逻辑：`AlarmService.list` → `AlarmStore.listInTimeRange` 时间窗过滤 → 条件过滤（level/service/ruleName）→ 关联触发事件（`config_alarm_event ⋈ config_event`，`listEventsByAlarmIds`，**已按 longConnServices 排除**）→ 排序分页。
- 表：内存 AlarmStore + `config_event` / `config_alarm_event`。
- SQL（`MetricQueryBuilder.alarmLinkedEventsSql`，参数化）：

```sql
SELECT rel.alarm_id, e.id, e.rule_id, e.rule_name, e.service, e.detection_way,
       e.level, e.status, e.message, e.group_key, e.silenced, e.triggered_at
FROM {db}.config_alarm_event rel
INNER JOIN {db}.config_event e ON rel.event_id = e.id
WHERE rel.alarm_id IN (?, ...) AND e.status = ?
  [AND e.service NOT IN ('长连接服务', ...)]
ORDER BY rel.alarm_id, e.triggered_at DESC
```

- 动态配置：长连接排除（§5）；过滤参数由前端传入。
- `/alarm/trend`：同源（AlarmStore）按 interval 分桶计数，无 SQL。

## 5. 告警规则（驱动告警列表/趋势的数据源头）

规则存于 Doris 表 **`config_event_rule`**（UNIQUE KEY(id)），由调度器每分钟评估
（`MonitorExecutorScheduler`，cron `apm.alarm.evaluation-cron`，默认每分钟）→ `EventRulePipeline` → `SingleMetricRuleEvaluator`。
阈值优先级：`query_json.thresholds.critical` > 行字段 `threshold`。

| 规则 | 指标 | 计算逻辑 | 表 | 默认阈值 |
|---|---|---|---|---|
| 服务入口平均耗时过高 | `service.avgDuration` | `SUM(sumDuration) / NULLIF(SUM(cnt),0) / 1e6`（毫秒），按 service 分组，60s 窗口 | `metric_service` | critical 1000ms（线上已调 3000ms），gt |
| 服务入口错误率过高 | `service.error.pct` | `SUM(error)/NULLIF(SUM(cnt),0)*100` | `metric_service` | critical 10，gt |
| 服务异常数过高 | `service.exception.cnt` | `SUM(cnt)` | `metric_service_exception` | critical 10，gt |

耗时规则标量 SQL（`metricAvgDurationScalarSql`）：

```sql
SELECT SUM(`sumDuration`) / NULLIF(SUM(`cnt`), 0) / 1000000 AS metric_value
FROM {db}.`metric_service`
WHERE `ts` >= ... AND `ts` < ... AND {分区裁剪}
  [AND 规则 from 标签过滤]
```

- 动态配置：规则行可经 `/api/v1/alarm/rules`（创建/删除/启停）管理；阈值在 `query_json.thresholds.critical`；**长连接服务额外在评估层排除**（`RuleMetricEvaluationService` 对 `*.avgDuration` 分组按 `longConnServices` 剔除）。

## 6. 动态配置汇总

### 6.1 traffic-light 配置（内存 + 持久化）

承载类：`TrafficLightService`（配置中心，含长连接服务语义的类级 javadoc）。
读写：`GET /cockpit/getConfig`、`POST /cockpit/setConfig`；持久化 `TrafficLightConfigPersistence` → cockpit 配置表；页面入口：故障排查页右上角「配置」抽屉（`fault/config-dialog.vue`）。

| 键 | 默认 | 作用域 |
|---|---|---|
| `errorRateThreshold` | 0.05 | 异常服务判定（错误率阈值） |
| `minRequestCount` | 10 | 异常服务判定（低于此请求量为灰=不健康） |
| `showServiceNumber` | 10 | 故障排查页每桶展示服务数 |
| `alarmRed` / `alarmYellow` | 2 / 1 | 故障排查 alarm 视角红黄阈值 |
| `exceptionRed` / `exceptionYellow` | 10 / 2 | 故障排查 exception 视角红黄阈值 |
| `longConnServices` | 空 | 长连接服务列表（逗号分隔），见 §6.2 |
| `nginxNoiseHosts` | 空 | nginx 接入噪音过滤：host 关键词（模糊匹配，忽略大小写），由 ai-apm-ingest 定时读取，命中整条丢弃 |
| `nginxNoiseUris` | 空 | nginx 接入噪音过滤：URI 关键词（模糊匹配，含 fullUri/uri） |

### 6.2 长连接服务排除 —— 统一收口

配置唯一来源：`TrafficLightService`（`KEY_LONG_CONN_SERVICES`）；过滤统一入口：
`longConnServices()` / `longConnServiceSet()` / `excludeLongConnServices(items, serviceGetter)`。

| 生效口径 | 实现方式 |
|---|---|
| 异常服务趋势 | `unhealthyServiceTrendSql` SQL `service NOT IN` |
| 慢调用统计（KPI/排行/下钻） | `CockpitMetricPortalService.applySlowExclusions` → DSL `service NOT IN`（查询携带 `durationRange` 过滤即判定为慢调用口径） |
| 耗时告警评估 | `RuleMetricEvaluationService` 对 `*.avgDuration` 分组剔除 |
| 红绿灯明细 / 服务告警趋势计数 | `TrafficLightService.trafficLight` 出口过滤 |
| 告警列表/趋势/计数 | `AlarmService.listAlarmsInQueryRange` 按告警 service 过滤 |
| 告警关联事件 | `ApmConfigRepository.listEventsByAlarmIds` SQL `e.service NOT IN` |

**不受影响**：请求量、错误率、异常数、服务总数（total），以及错误率/异常数类告警规则。

| 项 | 值 | 位置 |
|---|---|---|
| slow 列阈值 | >500ms | OtelConverter/SkyWalkingConverter |
| durationRange 桶边界 | 50/100/200/500/1000/3000 ms | DurationRangeUtil |

## 7. 已知口径注意事项

1. **error 的 4xx 差异**：nginx 流量 4xx 不算错误；OTLP/SkyWalking 取决于 agent 标记（OTel Java agent 当前语义 4xx 也标 ERROR）。同一服务不同接入方式错误数不可直接对比。
2. **错误率是"桶均值"不是占比**：`service.error` avg = 各时间桶 `SUM(error)` 的平均；占比口径另有派生指标 `service.error.pct = SUM(error)/SUM(cnt)*100`（告警规则使用）。
3. **灰=不健康**：异常服务趋势中低流量服务（total < minRequestCount）计入不健康数。
4. **getAlarmCount 的 noData 恒为 0**：`portalAlarmLevel` 只返回 2/3。
5. **服务入口 vs 组件**：`metric_service` 仅入口 span；`metric_service_http` 含出入口（用 `isIn='1'` 过滤入口口径）。
6. **长连接排除不含 total**：服务总数语义是实体数，不扣减。
